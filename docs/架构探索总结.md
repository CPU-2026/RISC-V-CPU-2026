# 架构演进史

项目从 2026 年 8 月的 RV32IM 软件周期模型起步，接入课程 AXI4-Lite 总线协议，从标量逐步扩成四宽超标量乱序核，最终以 `4603d03` 提交作为生产。以下是这次架构演进的过程。

## 8–10 月：将暑假完成的 CPU 仿真模拟器逐步完善成 RV32IM 的硬件核心

软件原型已经具备重命名、乱序执行和按序退休，但函数调用顺序会让后调用的模块提前看到同拍新值。项目改用 DarkSharpness 的模板，采用拍初读旧状态、拍末统一更新的硬件语义。架构主要发生了如下变化：
1. 采用 PRF 物理寄存器堆代替原来的逻辑寄存器副本，减少数据的搬运；
2. 采用 LQ、SQ 分离的架构代替原来 LSQ 耦合架构，分散职责；
3. ROB 用包含年龄位（epoch bit）和物理槽号的完整 tag 区分指令；
4. 使用手写的 Booth 编码、伪华莱士树来实现乘法，使用手写的 SRT-4 Radix 来实现除法；
5. 带寄存器 D$ 的早期实现中，D$ 约占总面积的 64%，于是改用项目自带的 FakeRam 来代替原来由寄存器实现的 D$ 和 I$；
6. 使用 spec-arch 模型和 ROB walk 来完成 RAT、PRF Freelist、RAS 的分支预测恢复；
7. 分支方向预测器由 TAGE 换到 Tournament，这是用简单实现换取面积的 Trade-off；
8. 引入 4 个缺失跟踪项（MSHR）并采用同行合并来实现非阻塞式 D$；
9. 课程版以退出 Store 退休冻结核心、对应 AXI B 握手结束计时，不再执行模拟器的 HALT 的全脏行排空行为。

这一阶段主要是完成单核 CPU 的实现，由于没有进行综合和 perf 的 IPC 测量，没有进行取舍。

## 10 月下旬–11 月 7 日：四宽的难点是供给和写回

超标量实现先做双退休，再扩取指、译码、分配和执行。双退休仍只消费拍初就绪的连续 ROB 前缀；批量分配必须处理组内 RAW/WAW，并让 RAT、PRF、ROB 与各保留站、访存队列按同一实际接受前缀推进。四宽最初用 ROB32／PRF64，后来经过消融实验发现 ROB16／PRF48 的 IPC 仅仅减少一点点，于是我们进行了一个 Trade-off：即用**少量 IPC 损失来换取可观的面积预算**。

我们为了提高 IPC 做了如下架构尝试：
- **执行单元与写回 CDB 的配套。** 10 月末同一 core 计时口径下，单 ALU 为 **0.829014 IPC**；双 ALU 共用整数写回只升至 **0.829644**，两路 ALU 各有写回才到 **0.859878**。于是我们进行了一个 Trade-off：即用**两根 CDB 的面积和频率开销来换取 IPC 收益**。独立双 AGU 试验确实发出了第二个地址，但整体 IPC 略降，并未采用。
- **空队列旁路比无条件加槽直接。** 空 IQ 可让 FQ 的译码组直接争取分配；旧 FQ/IQ 全空时，新取指包也能直达译码。原设计整组接受，否则整组落队列，不能重复消费。再做部分接受和后缀压紧没有减少原六周期，未采用。
- **四取指真正的收益来自去掉人为边界。** 我们进行了多种取指的对照实验：双取指、受限制的四取指、解除限制后的四取指，perf 几何 IPC 分别是 **1.063329／1.063798／1.137202**。两种四取指之间相差 **6.90%**。

## 11 月上旬：先定容量

完成四宽后，我们先做参数实验找容量。14 组配置、6 个程序、168 次对照显示：分配宽度 2→4 只再涨 **1.52%**，vvadd 还退化 **21.15%**；固定 PRF96 时，ROB 16→32 涨 **1.33%**，32→64 涨 **2.76%**；PRF 64→96 在这六个程序上完全没有收益。I$ 1→2 KiB 只让 towers 少 **43** 拍，2→4 KiB 没有额外收益，保留 **1 KiB**。

D$ 是反例最多的地方：8→16 KiB 的 IPC 有 **+5.55%**，但面积 **38112.64 μm²** 超限、Fmax 只有 **314.40 MHz**，不采用；基于 11 月 8 日另一条基线的 16 KiB 版面积 **35107.70 μm²**，曾在限额内采用，但 `Fmax²×IPC/Area` 反而降 **2.27%**，生产后来回到 **8 KiB**。四行 victim cache 面积合格，Fmax 只有 **293.16 MHz**，明确不采用。

最后用限流预取代替扩容：普通 RAM Load 真实接受后预取下一行，IPC **+2.46%**、Fmax **−1.98%**，评分 **+6.90%**，采用。

访存仲裁也做了取舍：Store 通常优先；只有 SQ 占用不超过 4 且无在途 Load 时，合格 Load 才能越过不重叠的普通 RAM Store 一次，随后必须先接受 Store。LQ 按真实退休释放，SQ 按内存实际接受释放；通知、候选和 `ready` 都不能代替真实授权。

`towers` 的返回失配也曾被误认为 RAS 太浅，实际峰值深度只有 1，问题是同 link 的 JALR 应只 push。**容量不是越大越好，先查行为，再找边际，最后用 PPA 决定。**

## 11 月 9–18 日：把预计算从晚授权里拆出来

回到 8 KiB 后，SRAM 先读和延迟展开把新流程基线定在 **316.11 MHz**；这是工具流程变化，不算 RTL 提频。三项组合优化（LSU 相邻字比较、分支旧空位判断、PRF 旧目的 tag 旁带）到 **333.35 MHz**，完整 Load 写回包再到 **346.31 MHz**。候选可以先算，实际 CDB 有效、身份和载荷仍由原获准来源决定。

跨模块反馈更难：后端接受数要经过 IQ 容量、译码数，最后才决定 FQ 能不能接收新包。双队列反向信用把晚算术改成旧态预计算、末级按实际接受数选择，到 **357.34 MHz**。这次按授权采用，但没有达到当时 400 MHz 或全组非退化要求，527 个稳定端点余量退化。

随后形成 Load 独占一路 CDB 的四写回结构，Load／StoreAddr 选择性晚唤醒，Branch 仍不能借 Load 当拍派发；恢复扩到每拍 **8 槽**，RAS 从已提交状态按程序顺序重放。八路 RAS 版在 **2.5 ns** 下是 **427.89 MHz**（同口径 W8／S 为 **399.03／422.27**），同一源码用 **2.0 ns** 重新映射只有 **395.37 MHz**。两者网表不同，不能把差值算作 RTL 收益。

## 11 月 19–24 日：从跨模块长链收敛到生产

以下是 **2.0 ns 映射与 STA** 的采用节点，不是每一步都加快，也不等同于逐条 Git 提交。当时部分版本虽未通过相应全组或违例门槛，仍按授权采用；这不改变原判定。

| 时间 | 采用的架构或实现变化 | 当时估计 Fmax（MHz） |
|---|---|---:|
| 11-19 | RAS 8→4 槽，保持八槽重放；随后 D$ 提前准备队首 Store 写载荷 | 455.313 → 472.107 |
| 11-19 | AXI 读队首、再加写队首同步保存缺失号；随后采用 Store→Load 同拍通知，原六未触发该旁路 | 472.979 → 471.455 |
| 11-20 | D$ 按物理请求槽比较命中标签；ROB 分 bank 预译码退休行；LSU 按在途槽准备 Load 返回候选 | 474.954 → 475.615 → 476.058 |
| 11-21 | ROB 入槽时保存 RAS 动作；SQ 队首预览 Store set；RAS 4→3，重放宽度不变 | 477.389 → 478.952 → 474.733 |
| 11-21 | D$ 赢家直选 SRAM set、另路编码槽号；ROB 预查完整 tag，保留 Load 同拍写回 | 478.058 → 482.564 |
| 11-22 | LQ8→4、SQ8→4，保留 8 个运输身份；AXI 写队首加应答地址旁带 | 476.501 → 477.389 → 479.625 |
| 11-23 | I$ 宏写使能与逻辑握手分开；D$ 在原读沿按 set 高位分组采样读掩码 | 483.703 → 484.619 |
| 11-24 | 从 11 月 23 日的仓库版继续开发，缩短 ROB 退休、D$ 查找和保留站写入路径 | **504.433** |

11 月 19 日只把 RAS 深度从 8 改成 4，Fmax 却从 395.37 提到 **455.31 MHz**：RAS 共享写使能的负载引脚从 17 个降到 9 个，SRAM 写使能从 8 个减到 4 个；深度参数也切换了重放实现，不能把收益全归给负载。2.0 ns 下仍有 3231 个违例。

晚期瓶颈在 ROB 退休、LSU 实际 Store 选路、D$ 掩码和前端 IQ 之间迁移；以 484.62 MHz 为基线的 **13 轮**测量里，第 12 轮「按请求槽分组」最快且合格，裸槽号、实时镜像和 3+4 预译码即使改善局部掩码，也没有实现整核提频。

### 11 月 24 日：在 11 月 23 日的仓库版上突破 500 MHz

我们从 11 月 23 日的 `9a1e26b` 继续开发，得到 [`4603d03`](https://github.com/CPU-2026/RISC-V-CPU-2026/compare/9a1e26b4ae89a8c278c037d9c9941b8b7975d829...4603d032754d6230a5e971cb06abf43c2e40277c)。旧版最紧的路径从 ROB 队首经过 Store 仲裁，一直走到 D$ 读掩码。我们主要改了三处：

- **四路退休。** 原来每路各比一次 tag 的年龄，现在四路共算一次队首到 flush 的距离，各自判断是否在 flush 之前。退休用的 tag、ready、SQ 槽号走窄读口，跟踪用的 PC 和指令分开读；旧物理寄存器是否需要回收，在重命名时就记入 ROB。
- **访存选路。** SQ 在 Store 地址到达时、D$ 在请求入槽时，各存一位退出地址匹配结果。D$ 先选需求请求，只在回退到预取时检查预取取消信号。读掩码沿用前一天按 set 高位分组的设计，但改为按候选槽提前采样，真正发起 SRAM 读时才使用。
- **前端和保留站。** FQ/IQ 在拍末存好空标志，下一拍判断旁路时不再算头尾指针之差。四路分配写入不同的 RS 槽，因此可以按掩码直接写，省去逐路优先选择；`busy` 等控制位仍复位，操作数和 PC 等宽字段则去掉异步复位。

两版都按 2.0 ns 做映射和 STA，整核估计 Fmax 从 **484.62 提到 504.43 MHz**，setup 违例端点 **25→0**（最紧余量 **+18.26 ps**），原六几何 IPC 同为 **1.10452**。采用时另与 **499.03 MHz** 的前生产版对照，违例端点是 **5→0**。

## 当前架构落点

默认每拍取指／译码／分配／退休各最多 **4** 条，执行仍是双 ALU、单 AGU；四路写回为两路 ALU、一路 Load、一路 MUL／DIV 共享。FQ8／IQ8、ROB16／PRF48，LQ4／SQ4 与 8 个 Load 运输身份分离；I$ **1 KiB**、D$ **8 KiB**，RAS **3 槽**、恢复每拍重放 **8 槽**。整核 **31,264.00 μm²**、**227** 个 SRAM 宏，2.0 ns 下 **27,528** 个计时端点全部满足 setup。详见[当前结构与参数](architecture.md)。

采用记录确认保断言的 sv2v 转换模型正确性 **19/19**，与 499 MHz 前生产的原六答案、周期和 **374,104** 条九字段退休逐拍、逐 lane 一致。[当前频率分析](频率分析.md)单独说明现网表的限制。

软件主树与模板树已同步到 `4603d03`：只改容量头，默认 **LQ4／SQ4／RAS3**，仍保留 8 个 Load 运输身份。两树的 Release 和断言版在原六用例上与转换 RTL 的答案、退休数及课程总周期全部一致，几何 IPC **1.104520180**。每树 **374,104** 条退休的周期、lane、PC、寄存器和 Store 载荷一致，指令字按 PC 从未被改写的镜像核对；五层调用与 LSQ 回绕定向测试也通过。见[验收证据](../../.cpu2026-synthesis/software4603d03-sync-20261124-r01/software-sync-verification.json)。本次未综合。
